## Non-negotiable product definition

Given a legitimate owner goal, constraints, current delegated permissions and
limited budget, ONE durable agent system must autonomously determine remaining
obligations, find/check useful sources and methods, compare alternatives,
execute only permitted effects, independently read back **owner-meaningful
results**, repair or switch approaches when evidence rejects them, resume
after interruption and validate transferable learning on unrelated goals.
It should reduce the owner's work supervising, finding defects and correcting
the agent's execution.

**Parent-system acceptance supersedes generic task-runner acceptance.**
The target product is the cognition PARENT for video/IP
(`video-growth-agent`), financial writing (`financial-writing-agent`),
novel writing (`novel-writing-agent`), A-share analysis/recommendation
(`a-share-event-driven-agent`), and future independent business
subsystems. Each domain retains its canonical product requirements,
IDs, domain authority, business state, sources, assets, work progress,
effect permissions and domain outcome oracle. The parent identifies
and reconciles owner goals, investigates needed knowledge, compares
applicable cross-domain methods, routes advice/work through the child's
admitted interface, coordinates dependencies and reads independent
business outcomes without overwriting child state.

**One cognition parent, two presently distinct technical surfaces.**
This ChatGPT/tool session participates as the actual parent's interactive
cognition and orchestration surface; the repository is the SAME parent's
prospective persistent Host, trusted adapters, state and independent
outcome-assurance implementation. Do NOT invent a separate preliminary
"developer cognition OS" or defer parent-cognition reliability to an
unrelated project. Research, goal fidelity, tool discovery, architecture
judgment, context rehydration, error correction and cost discipline are
core parent-system requirements NOW. Codex Goals/Hooks/Skills may help
implement them, but neither these configurations nor model self-report
prove reliable integration with the persistent Host, autonomous continuation
or independently verified video/article/novel/A-share business outcomes.

A successful local JSON draft or CSV comparison under the original contract
is a real **local scoped** result. It is not a claim that arbitrary owner
goals, remote-provider effects or a finished OS have passed.

## Six conditional future deployment/product gates — NOT prerequisites for current interactive acceptance

1. **Whole goal -> next legal choice.** With owner requirements (including
   conjunctive clauses), at least two genuinely applicable registered
   capabilities and independent counterevidence, the controller selects an
   executable **different** authorized next method without another chat turn.
   Missing acceptance clauses cannot disappear when delegating.
2. **Choice -> action -> independent correction.** The selected action runs
   through the ONE Host/Worker/SQLite grant and effect fence; source/provider
   state is independently re-read. Rejection causes a bounded alternative or
   evidence-gathering step, not a success claim, duplicate effect or endless
   alert loop. Distinct adverse, unchanged and reversal evidence are tested.
3. **Durable real host.** A real owner-approved schedule repeatedly invokes
   Host work while absent; crash and cold restart preserve exactly the same
   original goal, action identity, authorization and progress. Provider
   acknowledge-loss and retry behavior is tested on a permissioned sandbox.
4. **Correct authority and cross-domain repair.** Current grant, typed adapter
   scope, source trust, lease fencing, attempt/cost ceilings and independent
   readback gate external effects. Systemic defects are repaired at the
   shared responsible contract and tested across legitimate sibling paths;
   reviewer or model text cannot self-authorize or self-certify.
5. **Cross-domain parent-child generalization, not curated fixtures.**
   The SAME parent cognition loop must discover and cooperate with at least
   two distinctly governed real child domains, while honoring independent
   business identity, current domain requirements, permission and source
   authority. Evaluate conflicting/changed child state, parent guidance
   rejection, domain-specific independent readback and cross-domain
   method transfer/non-fit. Audit all four existing domains for no
   unintended authority or routing regressions, and independently
   exercise a NEW previously unregistered domain through a stable
   discovery/adapter contract without product-specific parent-code
   hardcoding. Measure actual child-relevant outcome and user correction
   burden; dry-run/read-only advice is not proof of business execution.
6. **Evidence attribution and product release.** Every result ties current
   original goal and grants to chosen method, actual executed effect, verifier
   identity, provider/source readback and unchanged/restored conditions.
   Independent reviewers can reproduce the claimed outcome; unknown stays
   unknown. Release still requires explicit owner authorization.

## Owner clarification 2026-11-27 — general system architecture and construction (INTERACTIVE ACCEPTANCE OPEN)

The parent must be useful not only for completing individual business tasks, but also for **designing, building, improving and validating other task systems, agent systems and professional workflows when the owner asks for them**. This is a first-class owner outcome, not a requirement to turn every ordinary request into a software project.

The owner supplies the intended result, constraints, preferences where material, and necessary authorization. The parent is responsible for discovering the relevant professional methods, tools and primary sources; decomposing the full requirement; challenging its own first interpretation and competing root causes; studying real implementations, call paths, tests and failure cases; comparing reuse/adapt/replace/remove/build; designing the appropriate architecture and workflow; and independently verifying the complete deliverable. Do not require the owner to provide a domain-expert checklist, enumerate tools, choose a framework, or operate routine test scenarios.

**No fixed pipeline is implied.** A task-specific dependency graph may branch, merge, parallelize, loop, pause, or be rebuilt as evidence changes. The decision/research loop and execution/feedback loop revisit upstream assumptions when a counterexample invalidates them. Depth is proportional to novelty, uncertainty, impact, risk and reversibility; a fixed number of research rounds, links, agents or documents is not an acceptance criterion. A simple one-off task must remain simple and must not incur irrelevant architecture/research overhead.

### System-construction result contract

When the actual goal requires a system, the acceptance target should cover the relevant subset of:

- complete requirement and constraint traceability back to original owner sources;
- system context, component responsibilities, boundaries and replaceable interfaces;
- data/state ownership, knowledge provenance and dependency invalidation;
- task-specific dynamic workflow, capability contracts and authorization/effect boundaries;
- failure classification, retries/idempotency, interruption recovery, rollback/compensation and observability;
- independent evaluation, positive/negative/neighbor cases and held-out tasks;
- runnable implementation or an explicit, evidence-backed reason a part remains unimplemented;
- operational, maintenance, cost and migration implications.

This is an acceptance vocabulary, **not a mandatory template or fixed stage list**. Do not build a larger system than the owner outcome needs. If only a design is authorized, do not silently implement or deploy; if implementation is authorized, a design document alone does not satisfy the implementation goal.

### Current architecture gap and evidence boundary

The current Draft architecture contains an evidence/decision graph, a bounded local planner, four registered native method contracts in `intent_planner.py`, and an explicit static execution registry in `capability_dispatch.py`. `native_decision.py` can preserve open-domain research proposals, but these proposals do not automatically become executable capabilities. This is a deliberate safety boundary, **not evidence that the Host already supports general system construction**. The current ChatGPT tool surface and repository Host are not assumed connected. See the candidate architecture decision in `docs/01-ARCHITECTURE-DECISIONS.md` §K. The evidence graph can represent multiple dependencies, but the current `task_dependencies` table keys on `task_id` and permits only one predecessor per successor; its dependency gate also admits only a narrow set of local task kinds. Therefore there is not yet a general executable multi-predecessor work DAG.

The acceptance experiment must compare the existing native model + currently available tools against any proposed work-graph/adapter change on the same unseen owner tasks. Add orchestration, a new framework, agent roles, a database, plugin auto-discovery or a new capability registry only if it produces a measured improvement in complete owner outcomes without weakening authority, independent verification, compatibility or cost. A mature framework may replace a deficient responsibility layer if the same-task evidence supports it; no framework is preselected.

**Native invocation boundary:** first-party client traces are required to claim that an installed Skill was selected before the first material decision. This current conversation's source inspection and tool use do not prove fresh-chat native Skill selection. Without an accessible first-party trace, keep that item NOT_TESTED. The repository candidate package now explicitly covers owner requests to architect/build/evolve another reusable task system, adds ordinary concept/one-off negative controls, and removes the default-prompt assumption that every invocation means editing the CAOS repository. The candidate package version is 0.1.25; CI packaging is not installation or publication, and does not close native-selection acceptance. The owner must not be asked to perform repetitive manual test ceremonies merely to satisfy the report; the agent should use authorized test clients, sandboxes and traces when available, and continue independent work when a particular client surface is not observable.

**Disposition remains NOT_READY.** No document update, static test, CI run, graph schema, model response or successful local build closes this acceptance area without independently verified unseen system-building and one-off negative-control outcomes.
