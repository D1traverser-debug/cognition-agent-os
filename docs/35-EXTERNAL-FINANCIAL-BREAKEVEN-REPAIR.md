# P24 — Prospectively pinned financial breakeven solver monotonic-direction repair

## Research question and constraints

Does a genuinely installed non-metered local Qwen2.5-Coder 7B produce a valid **numeric algorithm** repair for an externally reported, previously unfamiliar finance bug, instead of only succeeding on a literal ID-filtering issue? No paid or finite-credit hosted inference; no owner's Windows PC installation; no upstream PR, main merge, production release, or reference-patch fallback.

This P24 case is **distinct** from the NuPlan P23 substring/equality bug. P23 had two genuine first-try candidate successes but on a trivially small single-method task whose public issue contained a suggested one-line solution. P24 tests bracket direction, nonlinear monotonicity, negative search domain, endpoint targets and callback-driven model evaluation, not string replacement.

## Independent external issue and immutable original source

External issue: [anthropics/claude-cookbooks #931](https://github.com/anthropics/claude-cookbooks/issues/931). Reporter described a real monotonic decreasing breakeven solver yielding the incorrect boundary; for \`100 - 10*cost = 40\` the true answer is \`cost=6\` but the original method returns approximately \`0.0049\` on the range \`[0,10]\`. Source is pinned to issue's original public commit \`a162e0184e71b60290808a43961a6cbc8060123c\` at \`skills/custom_skills/creating-financial-models/sensitivity_analysis.py\`. Genuine upstream Git blob \`9674aad2e435917e60969d5b6daa816ccf7dc5b3\` independently checked before the experiment. No mutable-main substitution, no external repository writes.

The frozen original source is **not** a full NumPy/pandas financial package install in a Docker container. \`scripts/verify_p24_financial_breakeven.py\` verifies the full original upstream Git blob, extracts the exact original \`SensitivityAnalyzer.__init__\` **and** \`SensitivityAnalyzer.breakeven_analysis\` method bodies through source AST location, and places them in an isolated stdlib callback/JSON model adapter. This avoids pulling third-party dependencies into offline Docker while exercising the actual two original methods. Consequently any result supports only isolated solver-method repair, NOT the full financial package or external maintainer acceptance. A trusted independent AST scope review only permits changes to the \`breakeven_analysis\` implementation; the original constructor, method signature, frozen adapter and main entrypoint must remain intact. Agent candidate code executes only in non-root offline Docker.

## Frozen goal, public and heldout acceptance BEFORE model proposal

Four PUBLIC rows were authored from the issue's direction-defect semantics, not model outputs: reporter's linear decreasing example and one different nonlinear quadratic decreasing model each expected to fail on original source; two increasing-direction controls expected to pass. The original baseline must **exactly pass 2/4** or the task aborts before model request. A separate twelve-case AGENT-DERIVED HIDDEN set checks descending and ascending slopes, distinct coefficients, nonlinear monotonicity including negative-only domain, and exactly bracket-boundary roots. All hidden cases require both \`target_met: true\` and \`inside_bounds: true\`. The independent adapter calculates a candidate's returned root residual and interval membership using the model-output callback; expected labels are outside generated code and never passed to the proposer. Tests independently derive exact analytical roots from those case inputs as a falsifiable check on frozen expected values.

Both PUBLIC and HIDDEN, plus the original source bytes and reporter-compatible goal, are frozen in \`scripts/verify_p24_financial_breakeven.py\`, and independently inspected by \`tests/test_p24_financial_breakeven.py\`. That test also rejects source pin changes, constructor/signature modifications and injected top-level code. A SHA256 manifest of original blob, extracted source, goal, PUBLIC and HIDDEN is emitted by Docker baseline **before** inference. A successful repair requires: **real model candidate frozen**, PUBLIC **4/4**, sealed HIDDEN **12/12**, and independent original-method-only AST scope PASS. Failure to complete generation is a capacity failure, not a semantic rebuttal to a candidate that was never produced. A Docker test failure is not independent maintainer signoff.
